接入大模型后，提供自然语言转 SQL、SQL 解释与执行计划分析、索引建议、数据采样，以及**文档中心的文档问答**。

## 接入服务商

入口：**系统管理 → 系统配置 → AI 能力 → 服务商接入**。系统内置厂商模板，分「国内模型」与「海外模型」两组。

### 三步完成接入

1. **选择服务商**——从模板卡片中选择（通义千问、Kimi、DeepSeek、OpenAI、Gemini 等）
2. **填写凭证**——API Key 与端点；留空使用模板默认端点
3. **验证并保存**——系统会发起一次连通验证，结果显示在服务商列表的「状态」列

:::tip 端点怎么写
多数国内厂商提供 OpenAI 兼容端点，填到 `/v1` 即可；
Gemini 使用 `https://generativelanguage.googleapis.com/v1beta/openai`。
若厂商要求自定义路径，在「高级选项」里调整。
:::

### 关于凭证安全

- API Key 以 **AES-256-GCM 加密入库**，界面只回显掩码
- 编辑时**留空表示不修改**（不需要重新填一遍原值）
- 服务商可设为「共享」或「仅创建人可见」

### 常见接入问题

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 保存后状态「不可用」 | 端点不通或 Key 无权限 | 先在厂商控制台确认 Key 可用，再检查出网（走统一出网组件，8s 超时 + 重试 + SSRF 防护） |
| HTTP 200 但业务报错 | 业务错误码 ≠ 成功 | 看返回的 `error.message`，多为模型名不存在或余额不足 |
| 选不了某个存储/目标 | 不是 AI 模块问题 | 对象存储目标需先通过连通测试，见[备份恢复](./backup-restore.md) |

## 模型管理

| 配置项 | 说明 |
| --- | --- |
| 模型标识 | 调用时的 model 名称，需与厂商控制台一致 |
| 上下文长度 | 影响可提交的 SQL / 表结构长度 |
| 能力标记 | 对话、流式、工具调用、JSON 模式 |

## 使用方式

- **对话**——直接提问，可让它解释执行计划、给出索引建议
- **SQL 生成**——说明库表结构后让它写查询，生成的 SQL 请**务必**先在工作台以只读方式验证；也可让它直接调用工具，按库里的真实表结构来写
- **SQL 解读**——贴一条 SQL 让它解释结构、分析执行计划、推荐索引
- **数据探查**——让它抽取少量样本数据，确认字段的实际取值形态
- **慢查询解读**——结合[性能分析](./performance.md)的慢 SQL 明细，让它给出改写建议
- **文档问答**——在文档中心右下角唤起，问"备份失败怎么排查"这类问题，答案附文档链接

:::danger 边界
AI 生成的 SQL **不会**自动执行；涉及变更的语句仍须走工单与审批。
SQL 类工具全部只读：执行计划只跑 EXPLAIN，数据采样最多 50 行，索引建议只给 DDL 文本。
所有取数都要过数据授权，没有权限就直接返回提示，绝不绕过。
写操作只产草稿——创建工单、创建备份都要你在卡片上点「确认创建」才会落库，且分别受 `order.submit`、`backup.task.manage` 权限约束。
AI 调用会记录到调用日志，便于审计与成本核算。
:::

## AI 助手能调用哪些工具

AI 助手有两种回答方式：

- **通用技术问题**（原理、语法、方案选型、概念解释）——直接用大模型自身的知识回答
- **涉及平台真实数据的问题**（有哪些实例、昨晚备份是否成功、最近哪条 SQL 慢）——**去调用平台内置的工具取数，再基于真实结果作答**，不会凭印象编造

目前共内置 **17 个工具**：15 个只读工具 + 2 个写操作工具（生成草稿卡片，你点「确认创建」后才会真正落库）。

### 实例相关

**实例清单查询**
- 用途：列出平台已登记的实例，支持按关键字、数据库类型、环境过滤，返回地址、类型、环境、备注、连通状态与规格画像
- 适用：盘点实例资产、确认某个环境的实例范围
- 示例：「平台有哪些实例？」「生产环境有几个 MySQL 实例？」

**实例详情查询**
- 用途：查看单个实例的完整介绍——地址、类型、环境、连通状态、规格画像（数据库版本、操作系统、CPU/内存/磁盘、架构角色、高可用模式、运行时长），以及已采集到的库清单
- 适用：了解一台实例的家底，判断是否满足上线要求
- 示例：「192.0.2.10:3306 这台什么配置？」「这个实例上有哪些库？」
- 说明：库清单为空表示该实例**尚未同步元数据**，可先到实例管理里触发一次同步

**实例地址解析**
- 用途：把主机地址与端口解析成平台里的具体实例
- 适用：只有连接地址、不知道对应哪台登记实例时的第一步定位
- 示例：「192.0.2.10:3306 是哪个实例？」

### 库表结构

**库表清单查询**
- 用途：列出某实例下指定库的表清单，包含表名、表注释、行数估算与存储引擎
- 适用：快速了解某个库的表规模与结构分布
- 示例：「order 库有哪些表？」「哪张表数据量最大？」

**表结构查询**
- 用途：查看单张表的建表语句，含字段、类型、索引与列注释
- 适用：写 SQL 前确认字段名与类型、排查索引缺失
- 示例：「帮我看看 t_order 的字段和索引」「这张表有没有 name 字段？」

### SQL 生成与分析

这一组工具围绕「怎么写 SQL、为什么慢、该怎么建索引、表里装的是什么」展开，**全部只读**：
分析与建议只作为文本返回，任何变更都要走工单。

:::warn 统一的数据授权校验
这 5 个工具在调用任何查询之前，都会先按「库 / 表」校验你的数据授权：
只要 SQL 涉及的任意一张表没有查询权限，就**直接返回提示、不再执行任何查询**，
也不会把表结构或样本数据带出来。
:::

**SQL 生成（NL2SQL）**
- 用途：把自然语言需求转成 SQL 前的「结构准备」——按需求关键词在指定库里挑出候选表，返回这些表的字段、类型与索引，以及生成时必须遵守的约束，再由模型据此写出最终语句
- 参数：`question`（需求，必填）、`schema`（库名，必填）、`instance_id` 或 `host`+`port`、`tables`（可选，指定候选表）、`limit`（候选表数量，默认 3，最多 5）
- 适用：知道要查什么、但记不准字段名与索引时；避免模型凭印象编造字段
- 示例：「帮我写一条统计最近 7 天每个用户下单金额的 SQL」
- 返回示例：

```json
{
  "instance_id": "inst-xxxxxxxx",
  "schema": "order",
  "db_type": "MySQL",
  "question": "统计最近 7 天每个用户的下单金额",
  "table_count": 1,
  "tables": [
    {
      "table": "t_order",
      "comment": "订单表",
      "rows": "1204533",
      "column_count": 6,
      "columns": [
        { "name": "id", "type": "bigint(20)" },
        { "name": "uid", "type": "bigint(20)" },
        { "name": "created_at", "type": "datetime" }
      ],
      "indexes": ["PRIMARY(id)", "INDEX idx_created_at(created_at)"]
    }
  ],
  "constraints": ["只输出一条完整的 SELECT 语句……", "必须带 LIMIT……"],
  "instruction": "请基于上面的字段清单、索引与约束，用 SQL 代码块给出最终语句……"
}
```

**SQL 解释**
- 用途：把一条 SQL 讲成结构化说明——语句类型、涉及的库表、查询字段、JOIN 与关联条件、WHERE / GROUP BY / ORDER BY / LIMIT，以及风险提示（缺 WHERE、SELECT *、缺 LIMIT 等）
- 参数：`sql`（必填）、`schema`（可选，用于补全未限定库名的表）、`instance_id` 或 `host`+`port`（可选）
- 适用：接手别人的 SQL、Code Review 前先读懂一条复杂查询
- 示例：「这条 SQL 在干什么？」「这个查询有没有明显风险？」
- 说明：本工具只做**语法层解析，不执行 SQL、不查平台数据**；给了实例才会做授权校验，未给实例时结果里会带 `note` 明确标注「未校验数据授权」
- 返回示例：

```json
{
  "statement_type": "SELECT",
  "tables": ["orders.t_order", "orders.t_user"],
  "columns": ["`o`.`id`", "`o`.`amount`"],
  "joins": [{ "type": "INNER JOIN", "condition": "`o`.`user_id`=`u`.`id`" }],
  "where": "`o`.`status`=1",
  "order_by": ["`o`.`created_at` DESC"],
  "limit": "20",
  "summary": "这是一条 SELECT 语句，涉及对象：orders.t_order、orders.t_user……"
}
```

**执行计划分析**
- 用途：对一条 SELECT 跑 `EXPLAIN`，并把结果翻成能看懂的结论——全表扫描、有索引未使用、filesort、临时表、预估扫描行数
- 参数：`sql`（必填，不要自带 EXPLAIN 前缀）、`instance_id` 或 `host`+`port`、`schema`
- 适用：定位慢查询的根因；验证补索引的预期效果
- 示例：「这条查询为什么慢？」「看看这个 SQL 的执行计划」
- 说明：当前支持 MySQL 系与 PostgreSQL 系；**只执行 EXPLAIN，不执行原查询**
- 返回示例：

```json
{
  "instance_id": "inst-xxxxxxxx",
  "db_type": "MySQL",
  "sql": "SELECT * FROM t_order WHERE status = 1",
  "explain_sql": "EXPLAIN SELECT * FROM t_order WHERE status = 1",
  "duration": "12ms",
  "row_count": 1,
  "plan": [{ "table": "t_order", "access_type": "ALL", "possible_keys": "idx_status", "rows": 120000, "extra": "Using where" }],
  "summary": { "access_types": ["ALL"], "max_estimated_rows": 120000 },
  "findings": [
    { "level": "warn", "message": "t_order 走全表扫描（type=ALL），通常需要为过滤条件补索引或改写条件" },
    { "level": "warn", "message": "t_order 有可用索引 idx_status 但实际未使用（key 为空）……" }
  ]
}
```

**索引推荐**
- 用途：基于表结构与（可选的）SQL 给出索引建议——缺失索引候选、重复/冗余索引、无主键提示，以及低区分度列、长文本列的建索引注意点
- 参数：`schema` 与 `table`（必填）、`instance_id` 或 `host`+`port`、`sql`（可选，基于这条 SQL 的过滤/关联/排序列给建议）
- 适用：新表上线前的索引评估、慢查询优化时的补索引决策
- 示例：「t_order 表还需要建索引吗？」「这条 SQL 该建什么索引？」
- 说明：只给建议与 DDL 文本，**不执行任何变更**；确认要落地请用「创建工单」生成草稿。PG 侧会额外读一次 `pg_indexes` 补齐索引信息；若仍拿不到已有索引，结果里会带 `index_info` 提示「候选需人工复核」，不会断言缺失
- 返回示例：

```json
{
  "schema": "order",
  "table": "t_order",
  "column_count": 4,
  "index_count": 4,
  "existing_indexes": ["PRIMARY(id)", "UNIQUE uk_uid(uid)", "INDEX idx_uid(uid)"],
  "sql_columns": ["status"],
  "suggestion_count": 2,
  "suggestions": [
    {
      "priority": "low",
      "reason": "SQL 的过滤 / 关联 / 排序条件用到了列 `status`，但没有以该列开头的索引；不过该列类型偏「低区分度」……",
      "suggestion": "ALTER TABLE `t_order` ADD INDEX idx_t_order_status (`status`);"
    },
    { "priority": "low", "reason": "索引 `uk_uid` 与 `idx_uid` 的列完全相同（uid），属于重复索引", "suggestion": "评估后删除其中一个：ALTER TABLE `t_order` DROP INDEX `idx_uid`;" }
  ],
  "note": "以上仅为建议：索引会影响写入性能与优化器选择，落地前请在测试环境验证，并走工单审批"
}
```

**数据采样**
- 用途：从指定表抽少量数据行，确认字段的实际取值形态与数据分布
- 参数：`schema` 与 `table`（必填）、`instance_id` 或 `host`+`port`、`columns`（可选，只看这几列）、`where`（可选，简单过滤条件）、`limit`（默认 10，最多 50）
- 适用：不熟悉的表先「看一眼」再写查询；确认枚举字段到底有哪些取值
- 示例：「看看 t_order 里的数据长什么样」「抽 5 条 status=1 的订单看看」
- 说明：只生成并执行 `SELECT ... LIMIT n`；`where` 只接受简单的列比较条件，子查询、注释、多语句一律拒绝。结果是**抽样**，不能用于统计口径
- 返回示例：

```json
{
  "schema": "order",
  "table": "t_order",
  "db_type": "MySQL",
  "sql": "SELECT * FROM `order`.`t_order` WHERE status = 1 LIMIT 10",
  "row_count": 2,
  "columns": ["id", "uid", "status", "created_at"],
  "rows": [{ "id": "10001", "uid": "88", "status": "1", "created_at": "2026-10-15 09:12:33" }],
  "sampled_only": true,
  "note": "以上只是抽样结果（非全量）……长文本字段已截断，单值最多 200 字符"
}
```

无权限时的返回

只要涉及的表没有查询授权，工具不会执行任何查询，而是返回下面这段结构 —— 措辞在 5 个工具里完全一致：

```json
{
  "allowed": false,
  "code": "no_data_grant",
  "action": "select",
  "missing_objects": ["表 `order`.`t_order`"],
  "message": "你没有对 表 `order`.`t_order` 的查询权限，因此本次不执行任何查询，也不会返回该对象的表结构或样本数据。",
  "how_to_apply": "请联系平台管理员在「系统管理 → 权限管理」为你授予对应库表的数据授权（操作类型：查询）；授权生效后重新提问即可。若你认为自己已被授权，请确认授权主体与当前登录账号一致、且授权仍在有效期内。",
  "note": "请把上面这段提示原样转述给用户：不要改用其它工具、也不要换一种问法绕开权限取数，更不要依据常识猜测这些表的字段或数据内容。"
}
```

`generate_sql` 里如果只有**部分**候选表被拒，被拒的表会放进 `skipped_tables`，`skipped_message` 用的也是同一句话，其余有权限的表照常返回。

### 工单

**工单列表查询**
- 用途：按实例、状态、关键字筛选工单，也可做数量统计
- 状态包括：待审批、已通过、执行中、已完成、已拒绝
- 适用：日常跟进待办、统计某个环境的变更量
- 示例：「待审批的工单有几张？」「本周有多少张工单在执行中？」

**工单详情查询**
- 用途：查看单张工单的变更 SQL、回滚 SQL、当前状态与申请人
- 适用：复核某次变更到底改了什么、回滚语句是否齐备
- 示例：「工单 1024 改了什么？」「这张单有回滚 SQL 吗？」

### 备份

**备份状态查询**
- 用途：查看备份任务及**最近一次执行结果**——成功或失败、开始与结束时间、备份类型；支持按实例过滤或按任务名模糊匹配
- 适用：早班巡检「昨晚备份都成功了吗」、定位某个实例的备份异常
- 示例：「昨晚备份有没有失败？」「核心库的备份任务最近一次跑成功了吗？」

**创建备份**
- 用途：为某个实例准备一张备份任务草稿，覆盖物理备份（MySQL→XtraBackup、PostgreSQL→pgBackRest）与逻辑备份（mysqldump/pg_dump）
- 备份范围二选一：`ALL` 整实例（物理备份只能整实例）、`CUSTOM` 指定库（只有逻辑备份支持）
- **你核对后在卡片上点「确认创建」，备份任务即被创建并纳入调度**，无需再跳转创建页；创建人固定为当前登录的你自己
- 适用：把「说人话的备份需求」直接转成备份任务，省去在备份中心逐项填表
- 示例：「给 192.168.1.99:3306 建一个每天凌晨 1 点的物理备份」「每周二、周日 2 点对 order 库做逻辑备份，保留 30 天」

### 监控与性能

**告警查询**
- 用途：查询监控告警列表，可按实例、严重级别（P0 最严重 ~ P3）、时间窗过滤
- 状态包括：未恢复、已恢复
- 适用：接班时快速掌握当前未恢复告警、回溯某实例最近的告警历史
- 示例：「现在有哪些未恢复的告警？」「这台实例最近一周有告警吗？」

**慢查询查询**
- 用途：查看慢 SQL 记录（按耗时倒序），可按实例与时间窗过滤
- 适用：定位拖慢业务的语句，作为索引优化或 SQL 改写的起点
- 示例：「最近哪条 SQL 最慢？」「昨天这个实例耗时 top 的语句有哪些？」

### 写操作

**创建工单**

- 用途：为某个实例准备一张变更工单草稿，覆盖建库、建表、改表、DML 等常见变更
- **你核对后在卡片上点「确认创建」，工单即被创建并直接进入规范预审环节**，无需再跳转创建页或手动提交；预审结果可在工单详情页查看
- 工单的创建人固定为当前登录的你自己，与你对话时无需（也无法）指定
- 适用：把「说人话的需求」快速转成规范工单，省去手写 DDL
- 示例：「帮我在 test 实例建一张用户表，字段有 id、name、created_at」

:::warn 使用工具时的四个前提
1. **提问越具体，回答越准**——带上实例地址、库名、表名、工单号或时间范围，能明显提高命中率；只给一个模糊说法（例如「查一下最慢的语句」）时，助手可能取不到数据。
2. **只读工具遵守你的数据授权范围**——你无权访问的实例，AI 助手同样查不到，不会因为它而扩大权限。SQL 类工具还会下沉到「库 / 表」粒度，缺哪张表的权限会直接告诉你（见上文「无权限时的返回」）。
3. **查不到就直说**——工具返回为空时，助手会明确回答「当前没有查到相关数据」，并建议换个说法，不会编造数据或给示例值。
4. **建议不等于变更**——索引推荐只给 DDL 文本，助手不会替你执行；确认要落地请让它生成工单草稿，走审批后再执行。
:::
